Add a patch-based Artifact revision contract and a dedicated tool extension. A revision now costs the size of the change: callers send `$set`, `$unset`, `$push` and `$pull` instructions against a mandatory `baseRevision`, address one collection entry by field match or position, and receive the failing path plus a repair hint when a patch is rejected. A stale base revision reports the current revision — the response schema requires it on a `BASE_REVISION_CONFLICT`, so a conflict is always actionable — and says whether the patch can be resent as written — only an append at a fixed path, with no position and no filter — or has to be rebased against a fresh read. Every rejection carries a `repair` hint: the field is required, and it also states whether the failure proves nothing was persisted or leaves the outcome unknown. A patch request carries the same optional `statusPath` observation pointer a full revise does — one shared schema for both — and the host boundary receives the resolved previous revision, so a host layered over the lifecycle writer still emits status changes. A patch request can also name `representations` — an object replaces the rendering hints wholesale, `null` clears them, and an absent property keeps the previous revision's — so a caller can refresh a caller-authored summary that the change made stale without a full revise. A patch request can name a target `schemaVersion`: the patched result is validated against that version's registration and the host stores the new revision at it, which is how an artifact left at an older version by a kind bump is migrated — the caller writes the instructions that make the payload fit, the package carries no migration logic — and `SCHEMA_VERSION_MISMATCH` now names the registered versions; a migration only moves forward, may `$unset` a property the target schema no longer declares, and may carry no instruction when the payload already fits, while an instructionless patch at the base's own version is rejected as `NO_CHANGE`, and a success that moved the artifact reports `migration: { from, to }` so only a migration may validate with no applied instruction. A host can now also refuse a write deterministically by returning a structured rejection — a message plus optional per-path issues — which the tool reports as `STORE_REJECTED` with a repair that promises nothing was persisted, while a thrown store failure keeps its unknown-outcome `HOST_FAILED` semantics. The read extension now takes its prototype-safe JSON accessors from the shared contracts instead of its own copies.
